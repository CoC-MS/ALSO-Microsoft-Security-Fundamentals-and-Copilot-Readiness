3

Review existing administrator roles

Direct link to configuration in portalOpen privileged role assignments in PIM ↗

Use Privileged Identity Management (PIM) to review existing active and eligible assignments across Azure and Microsoft Entra roles. Confirm each assignment has an owner and business need, remove stale access, and use eligible, time-bound assignments where appropriate.

If you do not use PIM, try the free Need4Admin script to generate an administrator access report. It reports active and eligible Entra and Azure roles, account status, MFA and authentication methods, and other account details.

Download the free Need4Admin administrator review script ↓
4

Create and secure emergency-access (break-glass) accounts

Create at least two cloud-only emergency-access accounts using your tenant's onmicrosoft.com domain. Assign them the Global Administrator role permanently, rather than making them dependent on PIM activation. Reserve these accounts for emergencies, not everyday administration.

Protect them with phishing-resistant authentication, such as FIDO2 security keys, and securely store credentials and spare keys. Avoid dependencies on the same authentication methods or infrastructure used by your regular administrators. Review Conditional Access exclusions so emergency access remains available during a lockout without leaving the accounts unprotected.

Alert on every sign-in and account change, document the recovery procedure and authorized custodians, and test access regularly. Follow the supplied PDF guide when configuring and validating these accounts.

Download the break-glass account best practices guide (PDF) ↓
5

Allow strong authentication methods

Direct link to configuration in portalOpen authentication methods ↗

Review Authentication methods > Policies. For internal users, start with Microsoft Authenticator passwordless sign-in and move toward phishing-resistant MFA. Require device-bound passkeys or FIDO2 security keys for administrators; consider synced passkeys for internal users where supported by your authentication policy and client platforms.

Authenticator phone sign-in is passwordless, but it is not phishing-resistant. Use Conditional Access authentication strengths to enforce the distinction. Pilot registration and recovery before removing weaker methods such as SMS and voice; review every enabled method and its target groups.

Learn more about Authentication methods
6

Fine-tune SharePoint and OneDrive sharing

Direct link to configuration in portalOpen SharePoint admin center ↗

In the SharePoint admin center, expand Policies, and then select Sharing.

Review tenant-level and site-level external sharing, default link types, guest access, link expiration, and sensitive sites. Prefer specific-people links where appropriate and remove unnecessary broad access. Review Teams-connected sites too: Copilot respects permissions, including overly broad ones.

Manage SharePoint and OneDrive sharing
7

Review existing access in SharePoint and OneDrive using Data Access Governance in SharePoint

Direct link to configuration in portalOpen SharePoint admin center ↗

In the SharePoint admin center, go to Reports > Data access governance. Review the available permissions and sharing reports to identify overly broad access to SharePoint and OneDrive content. Work with site and content owners to remove unnecessary access before rolling out Copilot.

Report coverage and remediation capabilities depend on your SharePoint Advanced Management or Microsoft 365 E5 entitlement. Confirm the prerequisites and report availability for your tenant.

Learn more: Data access governance reports for SharePoint sites
8

Enable self-service password reset (SSPR)

Direct link to configuration in portalOpen Entra password reset ↗

Configure SSPR for a pilot group, review registration and authentication requirements, then expand to the intended users. For hybrid identities, validate password writeback prerequisites and licensing. Align reset methods with your recovery strategy so SSPR does not undermine strong sign-in controls.

Trust the device, protect the work

Endpoint management & security

Enroll first. Apply protection. Prove compliance. Then enforce access.

Intune + Defender
1 Enroll→2 Protect→3 Validate→4 Enforce
1

Require MFA when registering or joining a device

Direct link to configuration in portalOpen Entra device settings ↗

Before enforcing CA003, go to Entra ID > Devices > Device settings and set Require Multifactor Authentication to register or join devices with Microsoft Entra to No. Enforce this requirement with Conditional Access instead of the legacy device setting.

See the device registration MFA setting
2

Configure automatic Intune enrollment

Direct link to configuration in portalOpen Intune automatic enrollment ↗

In Intune > Devices > Enrollment > Windows > Automatic Enrollment, set the MDM user scope to Some for your licensed pilot group, then All intended licensed users when ready. Keep the standard MDM URLs unless your deployment requires otherwise.

The reference shows MDM scope set to All. Its Windows Information Protection (WIP) settings are legacy and are not part of this recommendation.

See the automatic enrollment reference
3

Choose supported platforms

Direct link to configuration in portalOpen Intune enrollment restrictions ↗

For macOS, configure an Apple MDM push certificate before enrolling devices. Record its owner and renewal process. If personal Macs are not allowed, use Apple Business Manager with Automated Device Enrollment and configure enrollment restrictions to block personally owned devices; Apple Business Manager alone does not block BYOD.

Use CA203 to require MFA for internal users during Intune enrollment. Review enrollment restrictions for Windows, macOS, iOS/iPadOS, and Android and allow only the platforms and ownership types your organization supports.

Review CA204 for internal users and CA109 for administrators. Configure your supported platform list and verify the actual policy conditions before enabling. Test unknown platforms and account for platform detection limitations; do not assume the template already matches your business.

Give your information the right boundaries

Data protection & Copilot readiness

Classification, permissions, and information protection matter before the first prompt.

Microsoft Purview
1

Restrict discovery of SharePoint sites and content

Direct link to configuration in portalOpen SharePoint admin center ↗

Use Restricted Content Discovery selectively to limit discovery of SharePoint sites in organization-wide search and Microsoft Copilot while you review permissions. In the SharePoint admin center, go to Sites > Active sites, select a site, open Settings, and enable Restrict content from Microsoft Copilot. Remove the restriction when the review is complete.

This does not change permissions or prevent direct access to content users can already access. It applies to SharePoint sites, not OneDrive. Review the SharePoint Advanced Management and Copilot prerequisites before enabling it.

Learn more: Restrict discovery of SharePoint sites and content
2

Start with the ALSO Purview baseline

Direct link to configuration in portalOpen Microsoft Purview ↗

Use the reusable PowerShell-based ALSO Microsoft Security Purview toolkit as a starting point for tenant settings, sensitivity labels, DLP policies, optional retention, and supported AI governance controls. Review the prerequisites and deployment report; do not apply the entire baseline without understanding its impact.

Get the ALSO Purview toolkit ↗
3

Classify, label, and reduce oversharing

Define a classification scheme your people understand. Pilot sensitivity labels, verify protection behavior across Microsoft 365 apps, and review SharePoint, OneDrive, and Teams permissions. Create DLP and retention policies only where supported by your licenses and business requirements.

Use the appropriate Purview explorers and reports to review results. Train users on labeling, sharing, and handling Copilot output; a label does not automatically correct every underlying access permission.

These settings help you get ready; they are not a certification of security or compliance.

How to use these export packages
  1. Download and extract the package. Check its inventory and checksums, and select only the policies for your supported platforms and licenses.
  2. Review the JSON and its dependencies. Use an import workflow compatible with the Microsoft Graph/Intune export schema; the ZIP is a container, not a file to upload directly to every admin-center screen.
  3. For Conditional Access, include the supporting groups and migration table in your migration workflow, remap references and emergency-access exclusions, and configure CA106's authentication context separately. Do not copy source group IDs into a new tenant unchanged.
  4. For Intune, review assignments, scope tags, platform requirements, and policy conflicts. Generate fresh Defender onboarding data in the target tenant and replace the included tenant-bound profile.
  5. Import Conditional Access disabled, test in a pilot, review reports and user impact, and enforce in stages. Expand to the full intended scope only after validation.
